# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`com.ringme.base` — a Spring Boot 4.1 / Java 25 REST API **base/skeleton** meant to be cloned as the starting point for new services (this is the `spring/base/4.0-jdk25-full` branch, migrated from the Boot 3.5 / Java 21 base). It ships the cross-cutting plumbing (JWT auth, request context, i18n responses, uniform error handling, an HTTP client wrapper, CORS, profiles) that domain modules build on top of. There is no business domain — only demo auth endpoints under `/v1/auth`. `AppCode` holds only generic response codes; each project defines its own domain-specific code enum rather than extending `AppCode`. **Lite vs full:** the `-lite` branches ship no 3rd-party infra; this **`-full`** branch adds opt-in (disabled-by-default) MySQL/MongoDB/RabbitMQ/Kafka integration on top — see the **3rd-party infra** section under Architecture.

## Commands

Uses the Maven wrapper (`./mvnw` / `mvnw.cmd`). **Java 25 required** — `maven-enforcer-plugin` enforces `[25,26)` at the `validate` phase and fails the build fast on a wrong JDK. Point `JAVA_HOME` at a JDK 25 before building. Note: since JDK 23 javac no longer auto-runs annotation processors found only on the classpath, so Lombok is declared explicitly in `maven-compiler-plugin`'s `<annotationProcessorPaths>` (version from the Spring Boot BOM) — without that, every Lombok-generated member (`@Getter`/`@Builder`/`@Log4j2`...) fails to compile.

```bash
./mvnw spring-boot:run                            # run locally, dev profile (http://localhost:8386/base)
SPRING_PROFILES_ACTIVE=prod ./mvnw spring-boot:run # run with prod profile (env-driven config)
./mvnw test                                        # run all tests
./mvnw test -Dtest=BaseApplicationTests            # single test class
./mvnw test -Dtest=AuthControllerTest#login_issuesTokenPair  # single test method
./mvnw clean package                               # build jar + copy deps into target/lib
```

The build is configured for an **exploded (non-fat) jar**: `maven-jar-plugin` sets `mainClass=com.ringme.base.BaseApplication` with `classpathPrefix=lib/`, and `maven-dependency-plugin` copies all dependencies to `target/lib/` during `package`. Run the built artifact with `java -jar target/base-0.0.1.jar` alongside its `lib/` folder.

**Docker & CI.** `Dockerfile` is multi-stage (build on `maven:3.9-eclipse-temurin-25`, run on `eclipse-temurin:25-jre`) and copies the exploded `base-0.0.1.jar` + `lib/` — `docker build -t base . && docker run -p 8386:8386 base` (defaults to dev profile; pass `-e SPRING_PROFILES_ACTIVE=prod` + secrets for prod). GitHub Actions (`.github/workflows/ci.yml`) runs `./mvnw -B clean verify` on JDK 25 for pushes/PRs.

API docs (Swagger UI): `http://localhost:8386/base/swagger-ui.html`.

## Configuration & profiles

App-specific properties use the **`app.*`** prefix (`app.jwt.*`, `app.domain.*`, `app.img/audio/avatar.*`, `app.cors.*`, `app.rate-limit.*`) — matching the `@Value`/`@ConfigurationProperties` paths in `AppConfig`/`SecurityConfig`/`RateLimitProperties`. They sit under the same `app` namespace as `app.profile`. Infra properties stay at the root: `cache.*`, `rest-template.*`, `required.*`, `app-security`. Most values are overridable via env vars with sensible defaults (e.g. `${JWT_ACCESS_TTL:86400}`).

**Config layout (per-profile folders).** Only one `application.yaml` sits at the root of `resources/` — it holds the app name, the active-profile wiring, the profile-directory import, and the **Spring Cloud Consul** block (Consul must live here because `spring.config.import: consul` is resolved very early at bootstrap and can't come from a profile file). Environment-specific config lives under `resources/profiles/<profile>/`, split into small files by concern: `server.yaml`, `web.yaml`, `security.yaml`, `redis.yaml`, `http-client.yaml` (RestTemplate pool/timeouts/retry), `cache.yaml`, `observability.yaml` (actuator), `resilience.yaml` (Resilience4j circuit breaker + rate limiter + `app.rate-limit` filter behavior), plus one file per **3rd-party infra**: `mysql.yaml`, `mongodb.yaml`, `rabbitmq.yaml`, `kafka.yaml` (all opt-in, disabled by default — see the **3rd-party infra** section below). (The former monolithic `integration.yaml` was split into `http-client`/`cache`/`observability`/`resilience`.)

```yaml
# application.yaml (root)
app:
  profile: ${SPRING_PROFILES_ACTIVE:dev}
spring:
  application:
    name: base
  profiles:
    active: ${app.profile}
  config:
    import: optional:classpath:/profiles/${app.profile}/   # import the whole directory
```

**How the directory import resolves arbitrary file names.** Native Spring `spring.config.import` does **not** support wildcards/globs on the classpath; a directory import only loads files whose base name appears in `spring.config.name` (default `application`). To load the split files without listing each in `spring.config.import`, `spring.config.name` is set to `application,server,web,security,redis,http-client,cache,observability,resilience,mysql,mongodb,rabbitmq,kafka` — `application` must stay in the list so the root `application.yaml` (which holds the import directive) is itself loaded. Because `spring.config.name` is resolved too early to be set from inside a config file, it is supplied at the two entry points:
- **Runtime** (`java -jar`, `spring-boot:run`): `BaseApplication.main()` calls `SpringApplication.setDefaultProperties("spring.config.name", "application,server,web,security,redis,http-client,cache,observability,resilience,mysql,mongodb,rabbitmq,kafka")`, so it travels with the jar — no env var needed.
- **Tests** (`@SpringBootTest` does not call `main()`): the `maven-surefire-plugin` `systemPropertyVariables` set the same value.

Keep those two values in sync when adding/removing a split file. Adding a new environment = create `resources/profiles/<name>/` with the same set of files and run with `SPRING_PROFILES_ACTIVE=<name>` (no edit to `application.yaml` needed). Current folders: `dev` (default; permissive CORS, bundled dev keys), `uat`, `prod` (Swagger off; keys/CORS/secret forced from env).

**Secrets & JWT keys:** `app-security` and the JWT key paths must come from the environment in real deployments (`APP_SECURITY`, `JWT_PRIVATE_KEY_PATH`, `JWT_PUBLIC_KEY_PATH`) — see `.env.example`. The keys at `src/main/resources/keys/{public,private}.pem` are **dev-only** and loaded by classpath path via `RsaKeyLoader`. Each project cloned from this base MUST regenerate its own keypair (PKCS#8 private + X.509 public) — use the helper script (wraps openssl, has an overwrite guard):

```bash
./scripts/generate-keys.sh             # → src/main/resources/keys (Linux/macOS/Git Bash)
./scripts/generate-keys.ps1            # Windows PowerShell (needs openssl in PATH)
```

## Architecture

**Request lifecycle (filter order matters):**
1. `RequestContextFilter` (`@Order(HIGHEST_PRECEDENCE)`, registered as `customRequestContextFilter`) — wraps request/response in `ContentCaching*Wrapper`, builds a `RequestContext` from headers (`requestId`, `language`, `msisdn`, `deviceId`, `userAgent`, `clientType`, `role`, `revision`), stows it in a `ThreadLocal` via `RequestContextHolder`, puts `contextId` into Log4j2 `ThreadContext` (MDC) for correlated logging, and on completion logs the full request/response (bodies truncated to 4KB) to the `"request"` logger. Sensitive data is masked first via `LogMasker`: sensitive headers (`Authorization`, `Cookie`, ...) and JSON body fields (`password`, `accessToken`, `refreshToken`, ...) are replaced with `***` so tokens/passwords never reach the logs. Always clears the ThreadLocal and MDC in `finally`.
2. `JwtAuthenticationFilter` (added before `UsernamePasswordAuthenticationFilter`) — reads `Authorization: Bearer <token>`, delegates to `JwtAuthenticationServiceImpl` → `JwtProcessor` to validate and set the `SecurityContext`. The subject (username) becomes the principal, and the token's `roles` claim is mapped to `ROLE_`-prefixed authorities so `@RolesAllowed`/`hasRole(...)` work.

**Auth flow:** `POST /v1/auth/login` issues an access+refresh token pair, embedding roles in the `roles` claim — but `AuthServiceImpl.authenticateCredentials` rejects every request with 401 by default; implement it (real credential check returning the user's roles) to enable the endpoint. `POST /v1/auth/refresh-token` validates the refresh token and re-issues both, carrying the `roles` claim forward (in production you'd reload roles from your user store instead). `JwtProcessor` signs with RS512. Tokens carry a `type` claim (`access`/`refresh`); `JwtAuthenticationServiceImpl.authenticate` accepts **only `type=access`** for request auth, so a refresh token cannot be used to call APIs.

**Security** (`SecurityConfig`): stateless, CSRF disabled, CORS enabled (origins from `app.cors.allowed-origins`), JSR-250 method security enabled (`@EnableMethodSecurity(jsr250Enabled = true)`). Public paths: `/v1/auth/**`, `/troubleshoot/**`, `/actuator/health/**` (for LB/K8s probes), swagger/api-docs, `/v1/core/bonus-turn`, and all `OPTIONS`. Everything else requires authentication. These paths are relative to the `/base` context path.

**Inbound rate limiting** (`RateLimitFilter`, Resilience4j `RateLimiter`): **per-client-IP** fail-fast with `429` (`AppCode.CODE_429`) when one IP calls too often — each IP gets its own `RateLimiter`, built lazily from a shared template config (`RateLimiterConfig` read once from the registry) and held in a **bounded Caffeine cache** (`maximumSize` + `expireAfterAccess`), so one noisy IP can't starve others and the limiter map can't grow unbounded (idle IPs are evicted; the standalone limiters aren't registered in the registry, so eviction frees them). Runs after `RequestContextFilter` (so the `429` message is still localized) but before Spring Security (rejects before auth). **Opt-out + fully externalized:** per-IP thresholds live in `resilience.yaml` under `resilience4j.ratelimiter.configs.inbound` (a `configs` entry, not `instances`, since it's the template for the dynamic per-IP limiters; `limit-for-period`/`limit-refresh-period`/`timeout-duration`, env-overridable via `INBOUND_RATE_*`); filter behavior under `app.rate-limit` (`enabled` — set `false` and the filter bean isn't registered via `@ConditionalOnProperty`; `limiter-name`; `client-ip-header` for trusted-proxy `X-Forwarded-For` resolution, empty = `remoteAddr`; `max-clients`/`client-ttl` for the Caffeine cache bound + idle eviction; `excluded-paths` for probes/swagger/api-docs, matched after the `/base` context path is stripped). Bound by `RateLimitProperties` (`@ConfigurationProperties`). Still a **per-instance backstop** (N replicas ⇒ effective limit ≈ N × threshold); for a global IP limit, do it at the CDN/WAF/gateway or back it with Redis.

**Uniform responses — the core idiom.** Controllers do not build `ResponseEntity` by hand. Every response flows through the `AppCode` enum:
- `AppCode` holds `(code, message)` pairs and builds a generic `Response<T>` (`{code, message, data, metadata}`, nulls omitted) via `getResponse(...)` overloads.
- Success: `return AppCode.CODE_200.getResponse(payload);`
- The `message` is localized at build time: `getResponse` calls `getMessageLang()`, which looks up `MultiLangManager` (i18n) using the current request's `language`. **Caveat (documented in the code): `getMessageLang()` reads the request-scoped `RequestContextHolder` ThreadLocal, so it must run on the request thread — do not call `AppCode.getResponse()` from `@Async` or other off-request threads.**
- `AppCode` resolves its `MultiLangManager` lazily through `BeanUtil` (a static `ApplicationContext` holder) because enums can't be Spring-injected.

**Error handling:** throw `BusinessLogicException(AppCode, ...)` for expected/business errors. `GlobalExceptionHandler` (`@RestControllerAdvice`) returns the error `AppCode` in the response body **and** sets the HTTP status from `AppCode.toHttpStatus()` (4xx/5xx for known codes, `200` for codes that map to `OK` by default). `isLog`/`isTraceStackFull` flags control whether/how it's logged. Validation failures (`BindException`, `ConstraintViolationException`, `HandlerMethodValidationException`) are collected into a `{field: message}` map and returned as `CODE_400`. Any other `Exception` → `CODE_500`.

**Outbound HTTP:** extend `RestAbstractHttpClient` (implements `HttpClient`) and provide `defaultHeaders()`. It wraps a pooled `RestTemplate` (configured in `RestTemplateConfig` from `rest-template.*` in yaml) and centralizes error handling: `RestClientResponseException` is logged and the deserialized error body returned with the upstream status; connection-level failures return `503`. Per-call headers are merged over the defaults.

*Tuning for high concurrency (large systems):*
- **Pool** (`rest-template.*`): `max-total-connection`/`max-route-connection` are the real concurrency ceiling — with virtual threads enabled, many blocking calls queue on `request-timeout` (pool-lease timeout) once the pool is full, so size the pool to expected in-flight calls per upstream. `connection-ttl` recycles connections (avoid sticking to one backend behind an LB), `validate-after-inactivity` re-checks idle connections (reduces `NoHttpResponseException`).
- **Retry**: Apache HttpClient5 `DefaultHttpRequestRetryStrategy` (`retry-count`/`retry-interval`) retries **idempotent** methods on IO/stale-connection errors; POST is not retried.
- **Circuit breaker** (Resilience4j, `resilience4j-spring-boot4` starter — matching Boot 4): **opt-in** (not auto). Enable fail-fast (`503`) when an upstream is failing by passing a breaker to `RestAbstractHttpClient`'s constructor — either the shared `outboundHttpCircuitBreaker` bean, or **one breaker per upstream** via `super(restTemplate, circuitBreakerRegistry, "<name>")` (preferred for multiple upstreams, so one dead upstream doesn't trip another's breaker). Upstream 4xx/5xx (`RestClientResponseException`) are ignored by the breaker — only connection/timeout failures trip it. **All thresholds are externalized** to `resilience.yaml` under `resilience4j.circuitbreaker.configs.default` (the `default` config applies to every breaker, including per-upstream ones); `Resilience4jConfig` only resolves named beans from the auto-configured registries.
- **Metrics**: Apache's `httpclient5-observation` `ConnPoolMeters` publishes pool gauges (`http.client.pool.*`, tagged `httpclient=base-rest-pool`) to Micrometer — it replaces Micrometer's deprecated `PoolingHttpClientConnectionManagerMetricsBinder` (bound in `RestTemplateConfig.httpClient` off the `HttpClientBuilder`, so it must run after `setConnectionManager`); `/actuator/metrics` is exposed (auth-protected). Watch pending/leased vs max to detect saturation.
- **Outbound logging** (`LoggingInterceptor`): only logs (and buffers response bodies) when the logger is at DEBUG; sensitive headers/JSON fields are masked via `LogMasker`. Keep it off DEBUG in prod to avoid the buffering/throughput cost.

**Redis (cache + distributed lock), opt-in.** Config lives in its own per-profile file `profiles/<profile>/redis.yaml` using **native `spring.data.redis.*`** (not custom `app.*`). It is **disabled by default** (`spring.data.redis.enabled=false`) so the base builds/tests/runs with no Redis; the actuator Redis health indicator is tied to the same flag (`management.health.redis.enabled`) to keep `/actuator/health` UP when off. The connection factory is **auto-configured by Spring Boot** (standalone via `host`/`port`, or cluster when `spring.data.redis.cluster.nodes` is set — no custom factory). `config/cache/`: `CachingConfig` (`@EnableCaching`), `caffeine/CaffeineConfig` (always-on local `CaffeineCacheManager` (`CacheManager.CAFFEINE`) mapping per-cache TTL from `KeyCache` the same way — it's the default cache manager when Redis is off, and stays available **by name** for hot local caches when Redis is on), `redis/RedisConfig` (`@ConditionalOnProperty` — Jackson `RedisTemplate` + a `@Primary` named `RedisCacheManager` (`CacheManager.REDIS`) with default TTL from `AppConfig` and per-cache TTL from the `KeyCache` enum), `redis/RedissonConfig` (`@ConditionalOnProperty` — builds a `RedissonClient` for single **or** cluster from the same `DataRedisProperties`; connects eagerly, hence opt-in). On Boot 4, `RedisProperties` was renamed to `DataRedisProperties` and moved to `org.springframework.boot.data.redis.autoconfigure`; the value serializer uses Jackson 3's `GenericJacksonJsonRedisSerializer` (Spring Data Redis 4 drops the `2`/`3` suffix now that Jackson 3 is the default, and `java.time`/jsr310 support is built-in so no `JavaTimeModule` registration). `service/redisson/` provides `RedisDistributedService`/`RedisDistributedLocker` (Redisson distributed lock), also gated on the flag. `KeyCache` ships **empty** (skeleton) — each project adds its own cache-name constants + TTLs. Deps: `spring-boot-starter-data-redis` + `commons-pool2` + `org.redisson:redisson:4.6.1`. The enabled path is verified by `RedisIntegrationTest` (Testcontainers spins up a real `redis:7-alpine`; it self-skips when Docker is unavailable so `./mvnw test` stays green without Docker).

**Spring Cloud Consul (config + discovery), opt-in.** Added via `spring-cloud-starter-consul-config` + `spring-cloud-starter-consul-discovery` (Spring Cloud BOM `2025.1.2`, matching Boot 4.1). The whole block lives in the root `application.yaml` under `spring.cloud.consul.*` (must be there — `spring.config.import: optional:consul:` is processed at bootstrap, before profile files load). **Disabled by default** (`spring.cloud.consul.enabled=${CONSUL_ENABLED:false}`) so the base builds/tests/runs with no Consul agent — the `optional:consul:` import is silently skipped when off. Everything is env-overridable (`CONSUL_HOST`/`CONSUL_PORT`, `CONSUL_CONFIG_*`, `CONSUL_DISCOVERY_*`). When `CONSUL_ENABLED=true`: Consul Config (KV under `config/<app>/data`, YAML format, live-watch) is on by default; service **discovery/registration is a separate opt-in** (`CONSUL_DISCOVERY_ENABLED=true`, health check at `<context-path>/actuator/health`). No bootstrap starter is used (modern config-data approach). The enabled config-import path is verified by `ConsulConfigIntegrationTest` (Testcontainers real `hashicorp/consul`; self-skips without Docker). Note its mechanics: the config-import phase runs too early for `@DynamicPropertySource`, so the container's host/port/enabled are passed via **system properties** in a static block (cleared in `@AfterAll`), with a `@DynamicPropertySource` kept only to make the context-cache key unique.

**3rd-party infra (MySQL, MongoDB, RabbitMQ, Kafka), all opt-in & disabled by default.** This is the **`-full`** base (the `-lite` base ships none of these). Each infra has its own per-profile file (`mysql.yaml`/`mongodb.yaml`/`rabbitmq.yaml`/`kafka.yaml`) using **native Spring properties** (no custom `app.*`), every value env-overridable with a sensible default. The base **builds/tests/runs with none of them present** because each connects lazily and no listener/entity is declared in the base; each ships full **standalone config + a commented-out cluster/HA block** to uncomment when needed. Enabled paths are verified by Testcontainers tests under `src/test/java/com/ringme/base/infra/` (real `mysql:8.0`/`mongo:7`/`rabbitmq:3.13-management-alpine`/`apache/kafka:3.8.1`), each **self-skipping** (`assumeTrue`) when Docker is absent so `./mvnw test` stays green without Docker.
- **MySQL — JPA (Hibernate) + JdbcTemplate together** (`spring-boot-starter-data-jpa` + `mysql-connector-j`). Default-off via `spring.autoconfigure.exclude=${MYSQL_AUTOCONFIGURE_EXCLUDE:...DataSourceAutoConfiguration}` — excluding `DataSourceAutoConfiguration` makes JdbcTemplate/JPA/repositories all back off (no `DataSource` bean). **Enable:** set `MYSQL_AUTOCONFIGURE_EXCLUDE=` (empty) + creds (`MYSQL_URL`/`MYSQL_USERNAME`/`MYSQL_PASSWORD`) + `MYSQL_ENABLED=true` (health). Boot 4 FQN: `org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration`. HikariCP pool + JPA (`open-in-view:false`, batch) tunables externalized. Health key: `management.health.db.enabled`.
- **MongoDB** (`spring-boot-starter-data-mongodb`). **Boot 4 gotcha:** the Mongo connection prefix moved from `spring.data.mongodb.*` → **`spring.mongodb.*`** (`MongoProperties` is now in `org.springframework.boot.mongodb.autoconfigure`, prefix `spring.mongodb`); using the old prefix silently falls back to `localhost:27017`. The `uri` must include a database name or Boot 4 fails with "Database name must not be empty". **Enable:** `MONGODB_ENABLED=true` + `MONGODB_URI`. Health key: `management.health.mongodb.enabled` (Boot 4 renamed `mongo`→`mongodb`).
- **RabbitMQ / AMQP** (`spring-boot-starter-amqp`). Connects lazily; base declares no `@RabbitListener`. Listener/retry/prefetch tunables externalized. **Enable:** `RABBITMQ_ENABLED=true` + host/creds. Cluster = `spring.rabbitmq.addresses` (commented). Health key: `management.health.rabbit.enabled`.
- **Kafka** (`spring-boot-kafka` — **not** bare `spring-kafka`). **Boot 4 gotcha:** `KafkaAutoConfiguration` moved out of `spring-boot-autoconfigure` into the **`spring-boot-kafka`** module; depending on `spring-kafka` alone gives you the `KafkaTemplate` class but **no auto-configured bean**. `spring-boot-kafka` pulls `spring-kafka` transitively. String (de)serializers by default (JSON/SASL_SSL commented). No health indicator for Kafka — gate with the convention flag `KAFKA_ENABLED`. **Enable:** `KAFKA_BOOTSTRAP_SERVERS` (+ `admin.fail-fast:false` so a missing broker doesn't fail startup).

**Other config beans:** `AsyncConfig` (async executor), `ScheduleConfig` (scheduling), `ModelMapperConfig` (DTO mapping), `LocaleConfig`/`CustomLocaleResolver` (i18n from `i18n/messages*.properties`), `OpenApiConfig` (springdoc). Virtual threads are enabled (`spring.threads.virtual.enabled: true`).

## Conventions

- **Logging is Log4j2**, not Logback — `spring-boot-starter-logging` is excluded in `pom.xml`. Use `@Log4j2` (Lombok). Config: `src/main/resources/log4j2.xml`; logs are written under `logs/`. The dedicated `"request"` logger carries per-request access logs.
- Lombok throughout (`@Data`, `@Builder`, `@RequiredArgsConstructor`, `@Log4j2`). Prefer constructor injection via `@RequiredArgsConstructor` on `final` fields.
- Package layout by concern: `config/` (one subpackage per concern), `controller/v1` (versioned), `service` + `service/impl`, `dto/app/{request,response}`, `enums`, `exception`, `filter`, `security`, `client`, `context`, `converter`.
- Many code comments are in **Vietnamese**; Swagger `@Tag`/`@Operation` descriptions are too. Match the surrounding language when editing nearby comments.
- New endpoints: add the controller under `controller/vN`, return `AppCode.<CODE>.getResponse(...)`, and add any new public path to `SecurityConfig`.
- Domain response codes go in a **separate enum in the consuming project**, not in `AppCode` (which stays generic). Use `AppCode.matches(String)` / `TokenType.matches(String)` to compare against a raw code/value — note these are *not* `equals` overrides.

## Reusing as a template

See **`AGENTS.md`** for the full agent-facing rules (clone checklist + coding rules, in Vietnamese). Quick version:

When starting a new service from this base:
1. **Rename** `groupId`/`artifactId` in `pom.xml` and the `com.ringme.base` package (also update `mainClass` in the jar plugin and `@SpringBootApplication` package).
2. **Regenerate the JWT keypair** (see Configuration & profiles) — never inherit another project's keys.
3. **Set secrets** via env for non-dev (`APP_SECURITY`, key paths, `CORS_ALLOWED_ORIGINS`); copy `.env.example` as a starting point.
4. **Implement real authentication** in `AuthServiceImpl.authenticateCredentials` (rejects everything with 401 until you do) and return the authenticated user's roles.
5. Add your domain code enum, controllers under `controller/vN`, and any new public paths to `SecurityConfig`.
